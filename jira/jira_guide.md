# 📄 B102 Jira · Codex 팀 운영 가이드

> B102 팀이 Jira와 Codex를 일관되게 사용하기 위한 공통 운영 문서입니다.
> 기준: 1주 스프린트 · 개인별 40P · 하위 작업 미사용 · 일반 Task 중심 운영
## 1. 운영 원칙
1. **Codex는 B102 Jira의 가상 운영자다.** 요구사항을 읽고 중복을 확인해 에픽·스토리·Task 구조를 제안하며, 승인된 항목의 생성·연결·점검을 수행한다.
2. 팀원은 요구사항, 회의록, 버그, 아이디어 또는 “무엇을 해야 할까?”를 Codex에 전달한다. 정보가 부족하면 Codex가 필요한 내용을 먼저 질문한다.
3. 실제 구현·기획·테스트·배포 업무는 **일반 작업(Task)**으로 작성한다. Codex가 Task를 생성할 수 있지만 실제 작업자는 본인으로 지정한다.
4. SSAFY 집계에서 제외되는 **하위 작업(Sub-task)은 사용하지 않는다.**
5. Codex는 Jira 담당자로 지정되지 않는다. 에픽·스토리는 필요할 때만 실제 검토자·의사결정자를 담당자로 지정하고, 지정할 사람이 없으면 미지정으로 둔다.
6. Task는 관련 스토리와 **관련됨(relates to)**으로 연결한다.
7. Task의 상위 에픽은 연결한 스토리와 동일하게 지정한다.
8. 에픽과 스토리에는 포인트를 입력하지 않고 Task와 Bug에만 입력한다.
9. 개인별 주간 Task·Bug 합계는 **40P**로 맞춘다.
10. 요구사항 변경과 차단사항은 관련 스토리 댓글에 기록한다. Codex는 근거 없는 요구사항 변경, 담당자 추정, 완료 처리를 하지 않는다.
Jira 백로그: [B102 Jira](https://ssafy.atlassian.net/jira/software/c/projects/S15P21B102/boards/15309/backlog)
## 2. 이슈 구조
```javascript
Codex: 요구사항 접수 · 중복 확인 · 구조 제안 · 생성 · 점검
└─ 에픽: B102 도서 추천 서비스의 큰 목표 또는 기능 영역
   └─ 스토리: 사용자가 얻는 하나의 검증 가능한 가치
      ├─ 관련 Task: FE 작업
      ├─ 관련 Task: BE 작업
      ├─ 관련 Task: AI 작업
      └─ 관련 Task: QA·기획·배포 작업
```
Codex는 먼저 기존 에픽과 스토리를 조회한다. 맞는 상위 이슈가 있으면 Task를 연결하고, 없을 때만 새 에픽 또는 스토리를 제안한다. Task는 Jira의 실제 하위 작업이 아니라 독립된 일반 Task이며, 스토리와 `relates to`로 연결한다. 한 Task는 대표 스토리 하나에 연결하는 것을 권장한다.

- `1, 2, 3`만 사용한다.
- 모든 Task와 Bug는 **최대 3P**로 작성한다.
- 3P를 초과할 것으로 예상되는 작업은 독립적으로 완료·검증할 수 있는 여러 Task로 반드시 나눈다.
- 구현뿐 아니라 테스트와 검증 시간도 포함한다.
- 처음 사용하는 기술, 외부 API, 다른 파트 의존성이 있으면 한 단계 높게 책정한다.
- 포인트는 개인 평가가 아니라 주간 작업량을 조정하는 기준이다.
- 개인별 이번 주 합계는 40P로 맞춘다.

## 7. 상태 변경 규칙
```javascript
해야 할 일 → 진행 중 → 완료
```
- 담당자·포인트·스토리 연결·에픽·스프린트를 확인한 후 진행 중으로 변경한다.
- 코드 작성만 끝났다고 완료하지 않는다.
- 완료 기준과 테스트를 모두 확인한 후 완료로 변경한다.
- 작업이 차단되면 댓글에 원인과 필요한 협업을 기록한다.
- 요구사항이 바뀌어도 이슈를 삭제하지 않고 변경 내용을 기록한다.
- 모든 관련 Task가 완료되면 스토리도 완료 처리한다.
Task 상태에 따른 Story 자동 전환과 Mattermost 자동 알림은 Jira 자동화 설정이 필요하다. B102 프로젝트에서 설정 여부를 확인하기 전에는 자동 작동한다고 가정하지 않는다.
## 8. 협업자와 관찰자
- 스토리 담당자는 대표 책임자 한 명이다.
- 실제 작업자는 자신의 Task 담당자가 된다.
- FE·BE·AI 입출력 규격 변경을 반드시 알아야 하는 사람만 스토리 관찰자로 추가한다.
- 모든 사람을 관찰자로 추가해 알림이 과도해지지 않게 한다.
스토리에 필요하면 다음 내용을 추가한다.
```markdown
## 담당 및 협업

- 스토리 책임자:
- 프론트엔드:
- 백엔드:
- AI:
- 기획·QA:

## 변경 공유 원칙

- 요구사항 변경은 스토리 댓글에 기록한다.
- API·AI 입출력 변경은 관련 협업자에게 공유한다.
- 각 참여자는 본인의 일반 Task를 생성한다.
```
## 9. Codex 연결 및 사용 원칙
- 팀원은 각자 자신의 Atlassian 계정으로 Codex에 연결한다.
- Jira 계정, API 키, 인증 정보를 팀원끼리 공유하지 않는다.
- 처음에는 조회만 요청하여 계정과 프로젝트 연결을 확인한다.
- 생성·수정 전에는 Codex가 제안한 계획을 먼저 검토한다.
- 생성 후 Task 키, 포인트, 스토리 연결, 에픽, 스프린트를 다시 확인한다.

### Codex 백로그 설계 프롬프트
```javascript

자료:
- 여기에 요구사항, 회의록, 버그, 아이디어, 기존 이슈 키 또는 링크를 붙여 넣기

처리 원칙:
- 자료가 부족하면 임의로 이슈를 만들지 말고, 목표·사용자 가치·완료 범위·관련 자료 중 필요한 내용을 최대 3개씩 질문할 것
- Jira에서 기존 에픽·스토리·Task를 먼저 조회해 중복 여부를 확인할 것
- 맞는 에픽과 스토리가 있으면 재사용하고, 없으면 새 에픽·스토리를 제안할 것
- 에픽은 서비스 목표·기능 영역, 스토리는 사용자가 얻는 검증 가능한 가치, Task는 실제 수행 작업으로 나눌 것
- Sub-task는 사용하지 말 것
- Task 제목은 [요구사항코드-파트코드] 형식, 포인트는 1~3P, 3P 초과 작업은 분리할 것
- 담당자·기한·스프린트·완료 여부는 근거 없이 추정하지 말 것
- 지금은 생성하지 말고 이슈 유형, 제목, 목적, 완료 기준, 담당자, 포인트, 연결 관계, 미해결 질문을 표로 보여줄 것
```

## 12. Codex 가상 PM · 백로그 운영 프로토콜
<callout icon="🤖" color="blue_bg">
	Codex는 B102 Jira의 가상 PM이다. 요구사항을 구조화하고 에픽·스토리·Task의 생성과 연결을 관리한다. 다만 제품 결정을 임의로 내리거나 근거 없이 이슈를 생성·완료·삭제하지 않는다.
</callout>
### 12.1 Codex에 요청하는 방법
팀원은 요구사항·회의록·버그·아이디어·기존 Jira/Notion 링크 또는 GitHub/GitLab의 저장소·PR·커밋·비교 링크를 보내거나 “이번에 무엇을 해야 할까?”, “이 기능을 Jira로 만들어줘”, “내 커밋 읽고 Jira로 정리해줘”라고 요청한다. Codex는 실제 미래 업무와 기존 이슈가 있는지부터 확인한다. 운영 가이드만 전달된 경우에는 가이드를 이슈 생성 근거로 사용하지 않는다.
### 12.2 정보가 없을 때의 첫 질문
아래 문구를 그대로 사용한다.
```markdown
B102 도서 추천 서비스에서 무엇을 만들거나 고치려는지 알려주세요.

요구사항, 회의록, 버그, 기존 Jira 스토리/에픽 링크 또는 GitHub/GitLab의 PR·커밋·비교 링크를 보내주시면
Codex가 에픽·스토리·Task 구조를 확인할게요.
아직 자료가 없다면 아래 세 가지만 알려주세요.

1. 해결하려는 사용자 문제 또는 만들 기능
2. 사용자가 얻어야 하는 결과와 이번 스프린트 범위
3. 관련 화면·API·AI 기능 또는 참고 자료
```
일부 정보만 있으면 이미 받은 내용은 다시 묻지 않는다. 한 번에 최대 3개만 질문하며 목표·사용자 가치·완료 기준을 우선 확인한다. 커밋·PR만 주어진 경우 Codex는 변경 파일·커밋 메시지·diff를 먼저 읽고, 사용자 가치나 완료 기준이 불분명할 때만 질문한다. 담당자, 기존 스토리·에픽, 현재 스프린트, 중복 이슈처럼 Jira에서 읽기 전용으로 찾을 수 있는 정보는 먼저 조회하고, 선택이 모호할 때만 질문한다.
### 12.3 Codex의 이슈 분류 기준
- **에픽**: B102 도서 추천 서비스의 큰 목표·기능 영역·릴리스 단위다. 기존 에픽이 범위를 담으면 새로 만들지 않는다.
- **스토리**: 사용자가 얻는 하나의 검증 가능한 가치다. 목적과 완료 기준이 없으면 Codex가 먼저 질문한다.
- **Task**: 실제 구현·기획·테스트·배포 작업이다. 독립된 일반 Task만 사용하며 Sub-task는 사용하지 않는다.
- Codex는 아이디어·제안·확정된 업무를 구분한다. 확정되지 않은 항목은 이슈로 단정하지 않고 후보와 질문으로 표시한다.
- Task 제목은 `[요구사항코드-파트코드] 구체적인 작업 제목` 형식을 사용하고, 1P·2P·3P만 사용한다. 3P를 넘는 일은 완료·검증 가능한 단위로 분리한다.
### 12.4 제안부터 생성까지
1. Codex는 Jira와 제공된 자료를 읽고 기존 에픽·스토리·Task를 검색한다.
2. 재사용할 이슈와 새로 만들 이슈를 구분해 이슈 유형, 제목, 목적, 완료 기준, 담당자 또는 미지정 상태, 포인트, 연결 관계, 스프린트, 중복 여부를 표로 제안한다.
3. 정보가 부족하거나 선택지가 여럿이면 Codex는 최대 3개씩 질문한다. 담당자·기한·스프린트·우선순위·완료 여부는 추정하지 않는다.
4. 사용자가 “이대로 생성해줘”처럼 명시적으로 승인하기 전에는 Jira를 수정하지 않는다.
5. 승인 후 Codex는 에픽·스토리·Task를 생성하고, Task에만 Story Points를 넣으며, Task와 대표 스토리를 `relates to`로 연결하고 같은 에픽·스프린트를 적용한다.
6. 생성 후 이슈 키, 유형, 제목, 담당자, 포인트, 연결 이슈, 에픽, 스프린트와 미처리 항목을 표로 보고한다.
### 12.5 선개발 후 Jira 정리
팀원이 먼저 개발한 뒤 GitHub/GitLab의 저장소·PR·커밋·비교 링크를 보내면 Codex는 그 변경을 Jira 이력으로 정리한다.
1. Codex는 커밋 메시지, 변경 파일, diff, PR 설명과 테스트 흔적을 읽는다.
2. 실제 기능·버그 수정·테스트·배포 작업만 추출하고, 단순 포맷 변경·자동 생성물·의미를 알 수 없는 변경은 후보로 표시하거나 질문한다.
3. 기존 Jira 이슈를 검색해 이미 기록된 작업은 중복 생성하지 않고 연결 또는 갱신 후보로 제안한다.
4. 새 이슈가 필요하면 에픽·스토리·Task를 구분하고, 각 항목에 근거가 된 커밋 또는 PR을 함께 표시한다.
5. Codex는 이슈 유형, 제목, 설명, 완료 기준, 포인트, 연결 관계, 커밋·PR 근거를 표로 제안한다. 사용자의 승인 뒤에만 Jira에 생성하거나 수정한다.
### 12.6 Codex의 일상 관리 범위
- 요청 시 매일 또는 스프린트 점검을 읽기 전용으로 수행해 중복 이슈, 담당자 없는 Task, 연결 누락, 포인트 누락, 3P 초과 작업, 차단 상태, 완료 위험을 알려준다.
- 테스트 결과·PR·명확한 지시가 있을 때만 상태 변경이나 댓글 기록을 제안·수행한다.
- 이슈 삭제, 범위 축소, 담당자 변경, 완료 처리는 반드시 명시적 요청 또는 확인 가능한 근거가 있어야 한다.
### 12.7 매번 사용할 요청문
```markdown
B102 Jira 백로그를 Codex가 관리해줘.

아래 자료를 읽고 기존 Jira 이슈를 먼저 확인해줘.
맞는 에픽·스토리가 있으면 재사용하고, 없으면 새 에픽·스토리·Task를 제안해줘.

자료가 부족하면 임의로 만들지 말고,
목표·사용자 가치·완료 범위·관련 자료 중 필요한 내용을 최대 3개씩 질문해줘.
정보가 충분하면 생성하지 말고 초안을 표로 먼저 보여줘.
승인한 뒤에만 Jira에 생성·연결해줘.

자료:
- 여기에 요구사항, 회의록, 버그, 아이디어, Jira/Notion 링크 또는 GitHub/GitLab 저장소·PR·커밋·비교 링크를 붙여 넣기
```
