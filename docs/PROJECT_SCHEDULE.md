# 프로젝트 개발 일정 및 실행 순서

> 개인 맞춤형 도서 추천·개인 서재 서비스의 MVP 개발 순서입니다.
>
> 착수 2026-08-25(화) · 베타 배포 2026-09-14(월) · 최종 발표 2026-09-28(월)
>
> 기준: W0 착수 주차, W1~W4 개발 주차 (총 5주 · 추석 연휴 9/25 포함)

## 1. 가장 먼저 할 일

첫 작업은 추천 알고리즘 구현이 아니라 **MVP 범위와 공통 도서 데이터 모델을 확정하는 것**입니다.

1. 반드시 구현할 기능과 후순위 기능을 구분한다.
2. 여러 도서 API의 응답을 하나로 통합할 `Book` 공통 모델을 확정한다.
3. ISBN13을 기본 식별자로 정하고, ISBN10·서지번호·외부 API별 ID의 보조키 정책을 정한다.
4. PostgreSQL 테이블, Elasticsearch 문서, 백엔드 API DTO의 필드명을 맞춘다.
5. 개발·배포 환경에서 사용할 버전과 환경 변수를 확정한다.

이 다섯 가지가 정해져야 백엔드·프론트엔드·데이터 담당자가 서로 다른 형태의 도서 데이터를 만드는 일을 막을 수 있습니다.

## 2. MVP 범위

### MVP 한 문장

> 사용자가 도서를 검색하고 개인 서재에 기록하면, 좋아요·평점·독서 상태를 바탕으로 자신에게 맞는 도서와 추천 이유를 확인할 수 있다.

### 사용자에게 제공할 기능

- 회원가입·로그인·로그아웃 (가입 시 출생연도·성별 입력 — 신규 사용자 추천 세그먼트의 입력값)
- 초기 취향 설정: 관심 분야 선택 + 읽어본 책 선택·별점 (최초 로그인 1회, 건너뛰기 허용)
- 제목·저자 중심의 도서 검색 및 도서 상세 조회
- 개인 서재 등록·삭제
- 독서 상태 변경: 읽고 싶은 책 / 읽는 중 / 읽음 (날짜는 완독일 하나만, 미입력 시 오늘)
- 좋아요·평점 등록 및 취소·수정
- 도서별 한 줄 감상평 기록·수정·삭제 (MVP에서는 개인 기록 전용)
- 좋아요·평점·독서 상태를 반영한 콘텐츠 기반 개인 추천 (감상평은 MVP에서 미사용)
- 추천 근거 표시 (요약은 카드에 항상 노출, 상세 근거는 모달)

> **확정 — 좋아요와 '읽고 싶은 책'은 같은 기능으로 구현한다.** 좋아요를 누르면 `WANT_TO_READ` 상태로 서재에 등록하고, 좋아요를 취소하면 해당 서재 등록을 취소한다. 별도의 좋아요 테이블·API·버튼은 만들지 않는다.

### MVP를 위한 개발 기반 작업

사용자 화면의 기능은 아니지만 MVP가 동작하려면 아래 작업이 선행되어야 한다.

- 외부 도서 API 수집·정제·검색 색인
- 정보나루 도서관 마스터·관별 보유 원장·월별 대출 스냅샷 수집 (추천 수요와 근처 도서관 기능의 데이터 소스)
- PostgreSQL 저장 및 Elasticsearch 색인
- 행동 이벤트 수집 (추천 노출·클릭·이유 확인 — 지표 측정과 이후 추천 가중치의 원천)
- 테스트·Docker 실행·배포

### MVP에서 제외할 기능

- 협업 필터링 고도화
- 실시간 추천 갱신
- Kafka·RabbitMQ 기반 이벤트 파이프라인
- 별도 ML 서버와 복잡한 모델 운영
- 관리자 통계 대시보드
- Redis 기반 추천 결과 캐시
- 독서 메모·독서 진행률
- 도서 조회 기록 기반 추천
- 장르·출판사별 고급 검색 필터
- 추천 기준 세부 가중치 슬라이더 (프리셋만 제공)

위 기능은 핵심 흐름이 안정적으로 동작한 뒤 시간이 남을 때 추가합니다.

## 4. 단계별 작업 순서

### W0 (8/25~8/31). 기획과 데이터 계약 확정

#### 할 일

- 사용자가 완료해야 하는 핵심 흐름을 한 문장으로 정의한다.
  - `회원가입·로그인 → 초기 취향 설정 → 도서 검색 → 상세 확인 → 서재 등록·독서 상태 설정 → 좋아요·평점·감상평 기록 → 맞춤 추천·추천 이유 확인`
- 화면 목록과 API 목록을 먼저 만든다.
- `Book`, `User`, `LibraryItem`, `BookRating(review_text 포함)`, `Recommendation`, `UserEvent` 공통 모델을 정의한다.
- 좋아요를 `LibraryItem.status = WANT_TO_READ`로 처리하는 규칙을 API와 화면에 반영한다.
- 추천 응답 DTO에 `recommendationId`, `rank`, `reasonType`, `reasonText`를 포함하도록 계약을 확정한다 — 행동 이벤트가 이 값을 되돌려 보내야 지표가 연결된다.
- 도서 중복 판단 기준을 정한다.
  - 1순위: ISBN13
  - 2순위: 정규화한 ISBN10 변환값
  - 3순위: 제목·저자·출판일 조합은 검증용으로만 사용
- 외부 API 필드와 내부 필드의 매핑표를 작성한다.
- 필수값, nullable 값, 배열·문자열 변환 규칙을 정한다.

#### 완료 조건

- 모든 담당자가 같은 `Book` 모델을 사용한다.
- 검색·상세·서재·평가(선택 감상평 포함)·추천에 필요한 필드가 빠지지 않는다.
- 추천 응답·이벤트 필드 계약이 확정되어 프론트엔드가 목업으로 개발을 시작할 수 있다.
- API 명세 초안과 ERD 초안이 리뷰를 통과한다.

### W1 (9/1~9/7). 개발 환경·데이터 파이프라인·저장소

#### 환경과 뼈대

- `backend`, `frontend`, `data` 디렉터리를 만든다.
- Java 21·Spring Boot 3.5·Gradle 기준으로 백엔드를 생성한다.
- Node.js 24 LTS·React·TypeScript·Vite 기준으로 프론트엔드를 생성한다.
- Docker Compose에 PostgreSQL과 Elasticsearch를 구성한다.
- `.env.example`을 만들고 실제 키는 저장소에 올리지 않는다.
- GitLab CI에서 최소 빌드·테스트가 실행되도록 설정한다.

#### 데이터 파이프라인

- API별 수집 모듈을 분리하고 요청 제한, timeout, 재시도, 실패 로그를 구현한다.
- 응답 원본은 API별 디렉터리에 JSONL로 보관한다.
- ISBN 정규화와 중복 제거를 수행하고, 누락·오류 데이터를 별도 오류 파일로 남긴다.
- **정보나루 인기대출 API(`loanItemSrch`)로 세그먼트(연령×성별)별 상위 도서를 수집한다** — 세그먼트당 상위 N권 조회라 콜드스타트 폴백용 소규모 작업으로 운영한다.
- **관별 최신·3개월 전·24개월 전 보유 원장을 수집한다** — 누적 대출량은 후보 필터·prior에만 사용하고, 최근 수요는 스냅샷 차분으로 계산한다.
- 샘플 100~1,000건으로 정제 결과를 검증한다.

#### 저장소

- 사용자·도서·서재·평가·추천 이력·행동 이벤트 테이블을 설계한다.
- 도서관 마스터·관별 보유 원장·월별 수요 feature의 저장 위치와 갱신 주기를 설계한다.
- 도서 원천 데이터의 기준은 PostgreSQL로 두고 Flyway로 스키마 이력을 관리한다.
- 도서 검색용 Elasticsearch 인덱스 매핑을 만들고 ISBN13을 문서 식별자로 사용한다.
- PostgreSQL 저장과 Elasticsearch 색인을 분리해 색인 실패가 원천 저장을 막지 않도록 한다.

#### 완료 조건

- 새 팀원이 저장소를 내려받고 안내된 명령으로 백엔드·프론트엔드를 실행할 수 있다.
- 샘플 도서가 PostgreSQL과 Elasticsearch에서 같은 식별자로 조회된다.
- 세그먼트별 인기 도서 목록이 데이터로 존재한다.
- Flyway를 처음부터 실행해도 동일한 스키마가 만들어진다.

### W2 (9/8~9/14). 핵심 서비스 구현과 베타 배포

#### 백엔드 구현 순서

1. 공통 응답 형식·예외 처리·로그 정책
2. 회원가입(출생연도·성별 포함)·로그인·JWT 인증
3. 초기 취향 설정 저장 API
4. 도서 검색·페이지네이션·상세 조회
5. 서재 등록·삭제·독서 상태 변경
6. 좋아요(읽고 싶은 책)·평점·감상평 등록·수정·취소
7. **행동 이벤트 수집 API** (`recommendationId`·`rank`·이벤트 유형 저장)
8. 신규 사용자용 추천 조회 API — 세그먼트 인기 기반 폴백 + 추천 근거 응답

#### 프론트엔드 구현 순서

1. 공통 레이아웃·네비게이션·에러 화면
2. 로그인·회원가입·초기 취향 설정
3. 검색 결과·검색 조건·페이지 이동
4. 도서 상세·서재 등록·독서 상태 변경
5. 좋아요(읽고 싶은 책)·평점·감상평과 개인 서재 상태 필터
6. 추천 도서 목록과 추천 근거 (요약 노출 + 상세 모달)
7. **추천 노출·클릭·이유 확인 이벤트 전송** (IntersectionObserver 기반 노출 감지 포함)

#### 완료 조건 (= 9/14 베타 배포 체크리스트)

- 테스트 계정으로 핵심 사용자 흐름을 처음부터 끝까지 실행할 수 있다.
- 신규 가입 사용자가 행동 0건 상태에서도 추천과 추천 이유를 받는다.
- **행동 이벤트가 실제로 적재되는 것을 확인했다** — 로깅 없는 배포는 측정 기간을 그만큼 잃는다.
- 인증이 필요한 API가 비로그인 요청을 거부하고, 데이터가 사용자별로 분리된다.
- 로딩·빈 결과·API 오류 화면이 구분된다.
- 배포 후 팀 지인 대상 베타 사용자 모집을 시작한다.

### W3 (9/15~9/21). 개인화 추천 투입과 베타 운영

#### 구현 순서

1. 도서 텍스트를 제목·저자·주제어·책소개 중심으로 결합한다.
2. 텍스트를 정규화하고 TF-IDF 벡터를 만든다.
3. 코사인 유사도로 도서 간 유사도를 계산한다.
4. 사용자의 `WANT_TO_READ`(좋아요)·높은 평점·독서 상태를 가중치로 반영한다. 감상평은 MVP에서 사용하지 않는다.
5. 이미 읽었거나 서재에 등록한 도서를 제외한다.
6. 추천 이유를 함께 저장·응답한다.
7. 행동이 쌓인 사용자부터 폴백 추천을 개인화 추천으로 교체한다 — 행동이 없는 사용자는 계속 세그먼트 인기 폴백을 받는다.

#### 병행: 베타 운영

- 버그 트리아지·수정.
- 지표 적재 상태 주간 점검 (추천 클릭률·좋아요(읽고 싶은 책) 전환율·이유 확인률).

#### 완료 조건

- 신규 사용자와 기존 사용자 모두 추천 결과를 받는다.
- 추천 결과에 최소 한 가지 이상의 설명이 표시된다.
- 추천 계산이 실패해도 검색·서재 기능은 정상 동작한다.
- 폴백 기간과 개인화 기간의 지표를 비교할 수 있다.

### W4 (9/22~9/27). 통합 테스트·지표 집계·발표 준비

#### 할 일

- 회원가입부터 추천 확인까지 핵심 시나리오를 테스트한다.
- API 인증·권한·입력값·외부 API 키 노출 여부를 점검한다.
- 중복 요청·빈 데이터·외부 API 실패·Elasticsearch 중단 상황을 확인한다.
- PostgreSQL 백업·복구 방법을 문서화한다.
- 베타 지표를 집계한다 (클릭률·좋아요(읽고 싶은 책) 전환율·이유 확인률·폴백 대비 개인화 비교).
- 발표용 샘플 계정·데이터·시연 순서를 준비한다.
- **추석 연휴(9/25)를 고려해 발표자료·리허설을 9/23(수)까지 완료한다.**

#### 완료 조건

- 배포 환경에서 핵심 사용자 흐름이 성공한다.
- 치명적인 오류 없이 시연이 가능하다.
- 발표 자료에 실측 지표가 최소 두 개 이상 들어간다.
- README의 실행 방법과 실제 프로젝트가 일치한다.

## 5. 병렬 진행 기준

| 담당 영역 | 먼저 할 일 | 병렬로 가능한 일 | 반드시 기다려야 하는 일 |
| --- | --- | --- | --- |
| 데이터 | API 응답 분석·공통 모델 제안 | 수집기·정제기·인기대출 수집·샘플 데이터 제작 | 최종 DB 필드 확정 |
| 백엔드 | ERD·API 계약·인증 구조 | 초기 프로젝트·공통 응답·테스트 구조 | 공통 도서 모델 |
| 프론트엔드 | 사용자 흐름·와이어프레임 | 화면 컴포넌트·목업 화면 (MSW 등 목업 데이터 기반) | API 응답 계약 |
| 인프라 | Docker·환경 변수·CI 뼈대 | 개발용 서비스 구성·로그 정책 | 실제 배포 환경 정보 |

프론트엔드는 백엔드가 완성될 때까지 기다리지 않고 목업 데이터로 화면을 먼저 만들 수 있습니다. 단, W0에서 API 응답 형식이 정해져야 나중에 연결 비용이 커지지 않습니다.

## 6. 일정 지연 시 우선순위

일정이 밀리면 아래 순서로 기능을 줄입니다.

1. 협업 필터링과 고급 추천 모델 제거
2. Redis 캐시 제거
3. 관리자 통계와 부가 UI 제거
4. 지원 외부 API 수를 줄이고 핵심 API만 유지
5. 추천 주기를 실시간이 아닌 수동·정기 계산으로 변경
6. 개인화 추천(W3)을 줄이더라도 폴백 추천으로 발표 — 배포일은 미루지 않는다

**베타 배포일(9/14)은 지연 시에도 유지하고 배포 범위를 줄입니다.** 배포가 밀리면 측정 기간이 사라지고, 측정이 없으면 발표에서 지표를 말할 수 없습니다.
끝까지 유지해야 하는 기능은 로그인, 도서 검색·상세, 개인 서재, 사용자 행동 저장(이벤트 포함), 최소 하나의 추천 결과입니다.
