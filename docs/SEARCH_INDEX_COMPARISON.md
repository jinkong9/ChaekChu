# 한국어 도서 검색 인덱스 방식 비교 — PostgreSQL 안에서

작성 2026-09-02

전제 — 한국어 제목·저자 검색, L0 카탈로그 약 300만 행, EC2(T3.xlarge 16GiB) 한 대에 PG + Qdrant + Spring + 프론트, 정해진 프로젝트 기간.
Elasticsearch 를 띄우지 않고 PostgreSQL 확장으로 검색을 처리할 때의 선택지를 비교한다. B-tree 는 `LIKE '%…%'` 를 타지 못해 검색용으로 무의미하므로 제외한다.

<br/>

# 순위

| 순위 | 방법 | 한 줄 평 | 치명적 약점 |
| --- | --- | --- | --- |
| 1 | **PGroonga** | 검색 엔진을 PG 안에 넣는 것 | 인덱스 크기, 공식 PG 이미지 못 씀 |
| 2 | **pg_bigm** | 한국어 부분일치의 최소 해법 | 랭킹·다중컬럼을 손으로 짜야 함 |
| 3 | pg_trgm | 설치 0이지만 2글자 검색 불가 | 한국어 검색어 절반이 인덱스 못 탐 |
| 4 | PG FTS (tsvector) | `description`엔 최적, 제목엔 부적합 | `어린왕자`→`왕자` 불가 |
| 5 | mecab-ko 계열 | 이론상 최선, 현실은 빌드 지옥 | 유지보수 끊김 |

<br/>

## 1위. PGroonga

### 장점

| | |
| --- | --- |
| 다중 컬럼 가중치 | 제목·저자·출판사·소개를 인덱스 하나에 넣고 `ARRAY[10,8,3,1]`로 점수 |
| 검색 문법 | `김영하 OR 여행`, `-동화`, `"어린 왕자"` 내장. 사용자 입력 파서를 안 짜도 됨 |
| 부분일치 | Bigram이라 `어린왕자`→`왕자` 됨. 사전 관리 없음 |
| 부가 기능 | 전방일치 `&^`(자동완성), 하이라이트, 전각·반각·대소문자 정규화 |
| 확장 1개로 끝 | pg_trgm 병행 불필요 |

### 단점

| | |
| --- | --- |
| 인덱스 크기 | 300만 행 × 4컬럼이면 **수 GB**. `description` 포함 여부가 크기를 결정 |
| 한국어는 실질 bigram | `TokenMecab`은 일본어 사전 기본. 한국어 형태소는 mecab-ko-dic 별도 연결 — 사실상 안 함 |
| 자료 | 문서·이슈 대부분 일본어. 팀원이 모르는 기술 |
| PG 버전 종속 | 메이저 업그레이드 때 PGroonga 호환 버전 확인 필수 |

### 사이드 이펙트

| 영향 받는 곳 | 무슨 일이 생기나 | 대응 |
| --- | --- | --- |
| **Docker 구성** | 공식 `postgres:16` 이미지 못 씀. `groonga/pgroonga` 이미지로 교체 | 다른 확장(pgvector 등) 같이 쓰려면 커스텀 빌드 |
| **적재 배치** | INSERT/UPDATE마다 Groonga 인덱스 갱신 → 300만 행 초기 적재가 눈에 띄게 느려짐 | **적재 끝난 뒤 `CREATE INDEX`**. 인덱스 먼저 만들고 넣지 말 것 |
| **RAM** | Groonga 인덱스는 mmap. page cache에서 PG `shared_buffers`·Qdrant와 경쟁 | JVM처럼 고정 점유는 아니지만 인덱스 크기만큼 캐시 압박 |
| **백업/복구** | `pg_dump` 논리 백업은 인덱스를 안 담음 → 복구 시 **재빌드 시간** 추가 | 물리 백업이면 무관 |
| **복제** | 스트리밍 복제하려면 `pgroonga.enable_wal` 설정 필요 | 단일 노드면 해당 없음 |
| **쿼리 플래너** | `&@~`는 반드시 PGroonga 인덱스를 탐. 다른 WHERE 조건과 섞이면 recheck 비용 | 필터(장르·연도)는 검색 후 애플리케이션에서 or CTE로 분리 |
| **스키마** | `authors JSONB` 그대로는 가중치에 못 넣음 | `authors_text` 평문 컬럼 추가, 적재 시 함께 채움 |

<br/>

## 2위. pg_bigm

### 장점

| | |
| --- | --- |
| 부분일치 | `어린왕자`→`왕자` 됨. 2글자 검색이 인덱스를 탐 (pg_trgm과의 결정적 차이) |
| 단순함 | `LIKE '%q%'` 그대로. 기존 쿼리를 거의 안 바꿈 |
| 사전 없음 | 신조어·인명·외래어 제목에 강함 |
| RAM | 추가 프로세스 없음 |

### 단점

| | |
| --- | --- |
| 랭킹 없음 | 점수는 `CASE WHEN title = q … WHEN title LIKE q||'%' …`로 직접 |
| 다중 컬럼 | 컬럼마다 GIN 인덱스 따로. OR 조건은 BitmapOr로 합쳐지고 `ORDER BY CASE`는 후보 전체 정렬 |
| 1글자 검색 | 인덱스는 타지만 후보 폭발 → 느림. API에서 2글자 강제 |
| 릴리스 주기 | 개발이 느림. **쓰려는 PG 버전 지원 여부를 먼저 확인** |
| 설치 | contrib 아님. 배포판 패키지 없으면 소스 빌드 |

### 사이드 이펙트

| 영향 받는 곳 | 무슨 일이 생기나 | 대응 |
| --- | --- | --- |
| **Docker 구성** | 공식 이미지에 없음 → **PGroonga와 똑같이 커스텀 이미지 필요.** 설치 부담이 PGroonga보다 낮지 않음 | 이 시점에서 "그럼 PGroonga 쓰지"가 됨 |
| **적재 배치** | GIN 인덱스 갱신 비용. `fastupdate` pending list가 쌓이면 검색이 간헐적으로 느려짐 | 적재 후 인덱스 생성, 대량 갱신 뒤 `VACUUM` |
| **디스크** | 2-gram GIN은 원본 컬럼보다 큼. title 300만 → 수백 MB~1GB, authors 추가 시 그만큼 더 | 컬럼 수 최소화 |
| **recheck 비용** | 인덱스는 후보만 줌. 실제 `LIKE` 재확인이 heap에서 일어남. `이야`, `하는` 같은 흔한 bigram은 후보 수만 건 | `pg_bigm.enable_recheck`, `LIMIT` 필수 |
| **정렬** | `ORDER BY bigm_similarity()`는 인덱스 못 탐 | WHERE로 좁힌 뒤 정렬. 후보 상한 걸기 |
| **코드** | 점수 로직이 SQL CASE에 박힘 → 가중치 바꿀 때마다 쿼리 수정 | 나중에 PGroonga로 옮기면 다 버리는 코드 |

<br/>

## 3위. pg_trgm

### 장점

| | |
| --- | --- |
| **설치 0** | `contrib`. 공식 `postgres:16` 이미지에 이미 들어있음. `CREATE EXTENSION` 한 줄 |
| 부분일치 | 3글자 이상이면 `LIKE '%q%'` 인덱스 탐 |
| 유사도 정렬 | GiST 인덱스면 `ORDER BY title <-> 'q'`가 **인덱스를 탐** (KNN). 오타 허용 top-N에 유일하게 유리 |
| 안정성 | PG 코어 팀이 관리. 버전 호환 걱정 없음 |

### 단점

| | |
| --- | --- |
| **2글자 검색 불가** | `왕자`, `역사`, `경제` → 트라이그램 못 만듦 → seq scan. **한국어 검색어의 큰 비율** |
| 영어 기준 설계 | 한글 유사도 임계값(`pg_trgm.similarity_threshold`)이 튜닝 어려움 |
| 랭킹·다중컬럼 | pg_bigm과 같은 문제 (CASE 수작업) |

### 사이드 이펙트

| 영향 받는 곳 | 무슨 일이 생기나 | 대응 |
| --- | --- | --- |
| **응답시간 편차** | 3글자는 20ms, 2글자는 2초. **같은 검색창에서 어떤 단어는 빠르고 어떤 단어는 느린** 현상. 사용자에겐 버그로 보임 | 2글자 이하 → 전방일치 B-tree로 폴백하는 분기 코드 필요 |
| **T3 크레딧** | 2글자 검색마다 seq scan → CPU 크레딧 소모. 크레딧 바닥나면 전체 성능 계단식 하락 | 이게 시연 중 터지면 원인 못 찾음 |
| **인덱스 선택** | GIN(LIKE 빠름) vs GiST(KNN 정렬 가능) 택일. 둘 다 만들면 디스크 2배 | 용도 정해서 하나만 |
| **디스크** | 3-gram이라 pg_bigm보다 인덱스 더 큼 | — |

**한국어 프로젝트에서 이걸 고를 유일한 이유는 "지금 당장 Docker 이미지 안 바꾸고 시작"이다.** 나중에 pg_bigm/PGroonga로 갈 거면 처음부터 가는 게 낫다.

<br/>

## 4위. PG FTS (tsvector + GIN)

### 장점

| | |
| --- | --- |
| **설치 0, 사이드이펙트 최소** | 코어 기능. 어떤 이미지든 됨 |
| 가중치 | `setweight` A~D로 필드별 가중치 정식 지원 |
| 랭킹 | `ts_rank`, `ts_rank_cd` 내장 |
| 사용자 입력 파서 | `websearch_to_tsquery` — 따옴표·OR·`-` 처리 |
| 하이라이트 | `ts_headline` |
| **`description`에 최적** | 긴 문장은 띄어쓰기가 살아있어 어절 토큰이 잘 맞음 |

### 단점

| | |
| --- | --- |
| **제목 검색 실패** | `어린왕자`→`왕자` ✗, `왕자와`→`왕자` ✗ (조사). 접두 `:*`로 조사는 커버, 붙여쓰기는 불가 |
| 형태소 없음 | `'simple'` 설정은 공백 분리만. `'english'` 쓰면 한국어에 헛일 |

### 사이드 이펙트

| 영향 받는 곳 | 무슨 일이 생기나 | 대응 |
| --- | --- | --- |
| **테이블 크기** | `GENERATED … STORED` tsvector 컬럼이 행마다 저장됨. `description` 포함 시 테이블이 눈에 띄게 커짐 | 필요한 컬럼만. 또는 표현식 인덱스로 컬럼 없이 |
| **NULL 전파** | `to_tsvector(a) \|\| to_tsvector(b)`에서 하나라도 NULL이면 **전체 NULL → 검색에서 사라짐** | 모든 컬럼에 `coalesce(…, '')` 필수. 빠뜨리면 조용히 누락 |
| **`authors JSONB`** | 생성 컬럼은 IMMUTABLE 표현식만 → `jsonb_array_elements_text` 못 씀 | `authors_text` 컬럼 or 트리거 |
| **사용자 인식** | "어린왕자 쳤는데 안 나와요" → 검색 신뢰도 자체가 떨어짐. **기술 문제가 아니라 제품 문제로 번짐** | 제목 검색엔 쓰지 말 것 |
| **정렬** | `ORDER BY ts_rank`는 인덱스 못 탐. 후보 전체 계산 | `LIMIT` 필수 |

**순위는 4위지만 버리는 게 아니다.** 1위·2위 어느 쪽을 골라도 `description` 검색은 이걸로 따로 두는 게 정답이다. 공짜고 그 용도엔 제일 잘 맞는다.

## 5위. mecab-ko 계열 (textsearch_ko 등)

### 장점

| | |
| --- | --- |
| 진짜 형태소 | `여행을`/`여행하는`/`여행하면서` → `여행`. 이 그룹에서 유일 |
| tsvector 재활용 | 분석 결과를 PG FTS에 넣으니 `ts_rank`·`setweight` 그대로 |

### 단점

| | |
| --- | --- |
| **유지보수 끊김** | 한국어 PG 형태소 확장 대부분 수년간 방치. PG 16/17 빌드 실패 흔함 |
| 빌드 난이도 | MeCab + mecab-ko-dic + PG 확장 세 겹 컴파일 |
| 사전 관리 | 신간 제목·인명·신조어 미등록어 → 엉뚱하게 쪼개짐. 사용자 사전 계속 관리 |

### 사이드 이펙트

| 영향 받는 곳 | 무슨 일이 생기나 | 대응 |
| --- | --- | --- |
| **일정** | 빌드 성공까지 걸리는 시간이 **예측 불가**. 하루일 수도 일주일일 수도 | 시간 박스 정하고 실패 시 즉시 철수 |
| **Docker 이미지** | 커스텀 빌드 + MeCab 바이너리 + 사전 → 이미지 수백 MB 증가, 빌드 시간 증가 | — |
| **PG 업그레이드** | 매 메이저마다 재빌드, 빌드 실패 시 업그레이드 자체가 막힘 | PG 버전 고정 |
| **사전 변경 = 재색인** | 사용자 사전 추가하면 기존 tsvector와 불일치 → 300만 행 재색인 | 사전 변경을 배치로 묶기 |
| **팀** | 한 사람만 이해하는 컴포넌트가 됨 | — |

**정해진 기간의 팀 프로젝트에서 권하지 않는다.**

# 조합으로 보면

단독 선택이 아니라 실제로는 두 개를 쓴다.

```
1안  PGroonga (title, authors_text, publisher)  +  tsvector (description)
2안  pg_bigm  (title, authors_text)              +  tsvector (description)
```

`description`을 PGroonga/pg_bigm 인덱스에서 빼는 이유는 **인덱스 크기**다. 긴 텍스트를 bigram으로 쪼개면 인덱스가 폭발하는데, `description`은 어절 토큰으로 충분히 잘 찾힌다.

1안과 2안의 Docker 부담은 같다(둘 다 커스텀 이미지). 그래서 **2안을 고를 이유가 거의 없다** — 같은 비용으로 랭킹·다중컬럼·자동완성을 포기하는 셈이다. 2안이 맞는 경우는 PGroonga 설치가 막힌 관리형 DB(RDS 등)일 때뿐이다.
