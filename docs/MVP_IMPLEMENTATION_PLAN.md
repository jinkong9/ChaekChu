# MVP 구현 계획 및 작업 명령 기준

> 개인 맞춤형 도서 추천·개인 서재 서비스의 확정 MVP를 구현하기 위한 실행 기준입니다.
>
> 작업을 요청할 때 `1단계 진행`, `6단계 서재 API 구현`처럼 단계 번호를 지정하면 이 문서의 범위와 완료 조건을 기준으로 작업합니다.

## 1. 확정 MVP

### 사용자 핵심 흐름

```text
회원가입·로그인
  → 출생연도·성별 입력
  → 초기 취향 설정 또는 건너뛰기
  → 제목·저자 중심 도서 검색
  → 도서 상세 확인
  → 좋아요(읽고 싶은 책) 등록
  → 읽는 중·읽음 상태 변경
  → 평점 등록
  → 한 줄 감상평 기록(선택)
  → 개인 맞춤 도서 추천 확인
  → 추천 이유 확인
```

### 포함 기능

- 회원가입·로그인·로그아웃
  - 출생연도·성별은 신규 사용자 세그먼트 추천에 사용
  - 해당 정보는 다른 사용자에게 공개하지 않음
- 초기 취향 설정
  - 관심 분야 선택
  - 읽어본 책 선택 및 별점 입력
  - 최초 로그인 후 1회 표시
  - 건너뛰기 가능
- 도서 검색·상세
  - 1차 검색 조건은 제목·저자
  - 페이지네이션 지원
  - 상세 화면에서 서재 상태·평점 확인 및 변경
- 개인 서재
  - 독서 상태: `WANT_TO_READ`, `READING`, `READ`
  - `READ` 상태일 때만 완독일(`finishedAt`) 저장
- 좋아요와 읽고 싶은 책
  - 같은 기능으로 취급
  - 좋아요 버튼은 `WANT_TO_READ` 상태 서재 등록으로 처리
  - 좋아요 취소는 `WANT_TO_READ` 상태의 서재 등록 취소로 처리
  - 별도의 좋아요 테이블·API·버튼을 만들지 않음
- 평점
  - 1~5점
  - 사용자당 도서별 평점 1개
- 한 줄 감상평
  - 선택 입력, 최대 300자
  - 본인 독서 기록으로만 저장·조회·수정
  - MVP 추천·검색·AI 분석에는 사용하지 않음
- 추천
  - 행동 데이터가 없는 사용자는 정보나루 인기대출 기반 세그먼트 인기 도서로 폴백
  - 행동 데이터가 있는 사용자는 TF-IDF·코사인 유사도 기반 콘텐츠 추천
  - 이미 서재에 등록한 도서는 추천 결과에서 제외
- 추천 이유
  - 카드에 요약 이유 항상 표시
  - 상세 이유는 모달 또는 상세 영역에서 표시
- 측정 이벤트
  - 추천 노출: `IMPRESSION`
  - 추천 클릭: `CLICK`
  - 추천 이유 확인: `REASON_VIEW`

### 구현하지 않을 기능

- 협업 필터링
- 실시간 추천 갱신
- Kafka·RabbitMQ
- 별도 ML 서버
- 관리자 통계 화면
- Redis 캐시
- 독서 메모·독서 진행률
- 도서 조회 기록 기반 추천
- 장르·출판사별 고급 검색 필터
- 사용자가 추천 가중치를 직접 조절하는 기능

## 2. 구현 원칙

1. 추천 알고리즘보다 공통 데이터 모델과 핵심 CRUD를 먼저 완성한다.
2. PostgreSQL을 회원·도서·서재·평가·추천 이력의 원천 저장소로 사용한다.
3. Elasticsearch는 도서 검색과 유사 도서 조회용 읽기 모델로 사용한다.
4. 외부 API 원본 응답과 서비스용 표준 도서 데이터를 분리한다.
5. ISBN13을 표준 도서 식별자로 사용한다.
6. 외부 API에 ISBN13이 없는 데이터는 원본으로 보관하되 검색용 데이터에 넣기 전 검토한다.
7. Elasticsearch 색인 실패가 PostgreSQL 저장 실패로 이어지지 않게 한다.
8. 추천 계산 실패가 로그인·검색·서재 기능을 막지 않게 한다.
9. 모든 단계는 완료 조건과 테스트를 통과한 뒤 다음 단계로 진행한다.
10. MVP 범위 밖의 기능은 임의로 구현하지 않고 후순위 목록에 기록한다.

## 3. 구현 순서

| 단계 | 대상 | 선행 조건 | 완료 결과 |
| --- | --- | --- | --- |
| 0 | MVP·데이터 계약 | 없음 | 공통 모델·API·상태·추천 규칙 확정 |
| 1 | 프로젝트 뼈대·실행 환경 | 0단계 | 백엔드·프론트엔드·Docker 실행 |
| 2 | 도서 데이터 수집·정제 | 0단계 | 표준 JSONL·정제 결과 |
| 3 | PostgreSQL·Elasticsearch | 0~2단계 | 저장·검색 가능한 도서 데이터 |
| 4 | 회원·인증·초기 취향 | 1·3단계 | 가입·로그인·취향 저장 |
| 5 | 도서 검색·상세 | 3단계 | 제목·저자 검색·상세 조회 |
| 6 | 서재·독서 상태·좋아요 | 4~5단계 | 사용자별 서재 CRUD |
| 7 | 평점 | 4~6단계 | 사용자별 평점 저장 |
| 8 | 콜드스타트 추천 | 2~3단계 | 행동 없는 사용자도 추천 수신 |
| 9 | 개인화 추천 | 6~8단계 | 행동 기반 콘텐츠 추천 |
| 10 | 프론트엔드 통합·이벤트 | API 계약 | 전체 사용자 흐름 연결 |
| 11 | 테스트·베타·배포 | 1~10단계 | 배포 가능한 MVP |

좋아요는 별도 단계가 아니라 6단계 서재 상태 API의 `WANT_TO_READ` 동작으로 구현합니다. 평점은 MVP 추천 신호로 사용하고, 감상평은 기록 전용으로 저장합니다.

추천 후보·도서관 원장·월별 수요 계산의 상세 방향은 [추천 데이터 기반 서비스 방향](RECOMMENDATION_SERVICE_DIRECTION.md)과 [백엔드 ERD 초안](ERD.md)을 기준으로 합니다.

## 4. 0단계 — MVP·데이터 계약 확정

### 작업

- 화면 목록과 API 목록을 확정한다.
- `Book`, `User`, `LibraryItem`, `BookRating`, `Recommendation`, `UserEvent` 모델을 정의한다.
- 좋아요를 `LibraryItem.status = WANT_TO_READ`로 처리한다.
- 독서 상태를 `WANT_TO_READ`, `READING`, `READ`로 고정한다.
- `READ`일 때만 `finishedAt`을 저장한다.
- 외부 API 필드와 내부 필드의 매핑표를 만든다.
- ISBN13 정규화·중복 제거 규칙을 정한다.
- 추천 응답의 `recommendationId`, `rank`, `reasonType`, `reasonText`를 확정한다.
- API 에러 응답·페이지네이션·인증 실패 형식을 확정한다.

### 상태 규칙

```text
WANT_TO_READ → READING → READ
```

- 사용자는 상태를 직접 변경할 수 있다.
- `READ`로 변경할 때 완독일을 입력하지 않으면 서버 기준 오늘 날짜를 저장한다.
- `READ`가 아닌 상태에서는 `finishedAt`을 비운다.
- 사용자와 도서 조합의 서재 항목은 하나만 존재한다.
- `READING` 또는 `READ` 상태인 책을 `WANT_TO_READ` 취소만으로 삭제하지 않는다.

### 완료 조건

- 모든 담당자가 같은 필드명과 enum을 사용한다.
- API 명세 초안과 ERD 초안이 리뷰를 통과한다.
- 프론트엔드가 목업 응답만으로 화면을 만들 수 있다.

### 작업 명령 예시

```text
0단계 진행해줘. 현재 저장소와 database 문서를 읽고 Book 공통 모델, ERD 초안, API 응답 규칙을 문서로 작성해줘. 좋아요는 WANT_TO_READ 서재 등록으로 처리하고 별도 Like 모델은 만들지 마.
```

## 5. 1단계 — 프로젝트 뼈대·실행 환경

### 작업

- `backend/`에 Java 21·Spring Boot 3.5.16·Gradle 프로젝트를 생성한다.
- `frontend/`에 Node.js 24 LTS·React·TypeScript·Vite 프로젝트를 생성한다.
- `data/`에 Python 3.12 수집·정제 프로젝트를 구성한다.

- GitLab CI에서 백엔드 테스트·프론트엔드 빌드·Python 기본 검사를 실행한다.

## 6. 2단계 — 외부 도서 데이터 수집·정제

### 작업 순서

1. 국중·정보나루의 ISBN13 합집합을 L0 카탈로그 원천으로 구성한다.
2. API별 수집 모듈을 분리하고 timeout·재시도·요청 제한·실패 로그를 구현한다.
3. 원본 응답을 API별 JSONL로 보관한다.
4. 제목·저자·출판사·출판일·책소개·카테고리·이미지·ISBN을 표준 필드로 변환한다.
5. ISBN13을 정규화하고 API별 중복을 통합한다. L0 미등재 ISBN은 카카오 온디맨드 등록 대상으로 둔다.
6. 정제 실패 데이터와 실패 이유를 별도 파일로 남긴다.
7. 관별 보유 원장과 도서관 마스터를 보존하고, 최신·3개월 전·24개월 전 스냅샷을 준비한다.
8. 누적 대출 99% 유지 임계와 신간 트랙으로 추천 후보를 생성한다.
9. 샘플 100~1,000건으로 정제 결과와 스냅샷 차분을 검증한다.

### 표준 도서 필드

```text
isbn13, isbn10, title, subtitle, authors, publisher,
publishedDate, description, categories, keywords,
coverImageUrl, language, source, sourceBookId,
rawPayload, collectedAt
```

`keywords`는 보강 가능한 배치 feature이며 초기 PostgreSQL `books` 테이블의 필수 칼럼으로 저장하지 않는다.

### 완료 조건

- 동일한 ISBN13이 중복 도서로 생성되지 않는다.
- API 원본과 표준화 결과를 역추적할 수 있다.
- 누락·오류 데이터가 조용히 사라지지 않는다.
- 국중·정보나루 합집합 도서가 중복 없이 L0에 들어간다.
- 관별 원장에서 최근 3개월·24개월 대출 차분을 재현할 수 있다.
- 추천 후보와 신간 트랙이 `book_demand_features`로 연결된다.

### 작업 명령 예시

```text
2단계 진행해줘. database 폴더의 기존 API 샘플과 표준 규칙을 먼저 읽고, 외부 API 수집·ISBN 정규화·중복 제거·JSONL 출력 파이프라인을 구현해줘. 기존 샘플은 덮어쓰지 말고 테스트 결과와 오류 데이터 처리 방식도 보고해줘.
```

## 7. 3단계 — PostgreSQL·Elasticsearch 구축

### PostgreSQL 테이블 기준

| 테이블 | 주요 필드 | 목적 |
| --- | --- | --- |
| `users` | id, email, password_hash, nickname, birth_year, gender | 회원·세그먼트 정보 |
| `user_interests` | user_id, category | 초기 관심 분야 |
| `user_seed_books` | user_id, book_id, rating | 초기 취향 입력 |
| `books` | id, isbn13, title, authors, description, categories 등 | 표준 도서 원천 데이터 |
| `library_items` | user_id, book_id, status, finished_at | 개인 서재·독서 상태·좋아요 |
| `book_ratings` | user_id, book_id, rating, review_text | 평점·개인 감상 기록 |
| `recommendations` | id, user_id, model_version, generated_at | 추천 결과 묶음 |
| `recommendation_items` | recommendation_id, book_id, rank, score, reason_type, reason_text | 추천 항목 |
| `user_events` | user_id, recommendation_id, book_id, event_type, rank, created_at | 추천 측정 이벤트 |
| `libraries` | id, source_site_id, api_libcode, name, latitude, longitude | 도서관 마스터 |
| `library_holding_snapshots` | library_id, isbn13, snapshot_month, cumulative_loan_count, copy_count | 관별 보유·대출 원장 |
| `book_demand_features` | isbn13, loan_24m_count, loan_3m_count, rank_score, candidate_type, as_of_month, feature_version | 추천 후보·수요 파생 결과 |

### 저장 규칙

- `books.isbn13`은 unique로 관리한다.
- L0 카탈로그는 국중·정보나루 ISBN13 합집합이며, 카탈로그 출처는 `book_source_records`로 추적한다.
- `library_items(user_id, book_id)`는 unique로 관리한다.
- `book_ratings(user_id, book_id)`는 unique로 관리한다.
- `review_text`는 nullable이며 최대 300자로 제한한다. MVP 추천 입력에는 포함하지 않는다.
- `WANT_TO_READ`가 좋아요·읽고 싶은 책 등록을 의미한다.
- PostgreSQL을 원천 데이터로 두고 Flyway로 스키마를 관리한다.
- 1.2억 건 관별 원장은 PostgreSQL 트랜잭션 테이블에 무조건 적재하지 않고 Parquet/분석 저장소를 우선 사용한다.
- 개인정보는 추천 세그먼트 계산에 필요한 범위만 사용한다.

### Elasticsearch 기준

- 인덱스 예시: `books_v1`
- 문서 ID: ISBN13 또는 canonical book ID
- 검색 대상: title, authors, description
- exact 검색 필드: isbn13, publisher, categories
- 검색 결과에는 canonical book ID와 ISBN13을 함께 반환한다.
- 매핑 변경이 필요하면 기존 인덱스를 바로 수정하지 말고 새 버전을 만든다.
- 최신 보유 도서·근처 도서관 조회는 `libraries`와 최신 `library_holding_snapshots` 파생 데이터로 제공한다.

### 완료 조건

- Flyway를 처음 실행해도 동일한 스키마가 생성된다.
- 샘플 도서가 PostgreSQL과 Elasticsearch에서 같은 ID로 조회된다.
- 제목·저자 검색이 동작한다.
- 저장 실패·색인 실패 로그를 각각 확인할 수 있다.

## 8. 4단계 — 회원·인증·초기 취향

### 작업

- 회원가입 요청 검증을 구현한다.
- 비밀번호를 해시해서 저장한다.
- 로그인 성공 시 JWT를 발급한다.
- 인증 필터와 현재 사용자 조회 기능을 구현한다.
- 출생연도·성별은 세그먼트 추천에만 사용하고 공개 응답에서 제외한다.
- 관심 분야와 seed book 평점 저장·조회·수정 API를 구현한다.
- 초기 취향 설정은 건너뛸 수 있도록 한다.

### API 예시

```text
POST /api/v1/auth/signup
POST /api/v1/auth/login
GET  /api/v1/users/me
GET  /api/v1/users/me/preferences
PUT  /api/v1/users/me/preferences
```

### 완료 조건

- 중복 이메일 가입이 거부된다.
- 잘못된 비밀번호와 만료된 토큰이 거부된다.
- 인증이 필요한 API가 비로그인 사용자를 거부한다.
- 개인정보가 다른 사용자에게 노출되지 않는다.
- 취향 설정을 건너뛴 사용자도 서비스 이용이 가능하다.

## 9. 5단계 — 도서 검색·상세

### 작업

- Elasticsearch 제목·저자 검색을 구현한다.
- 페이지 번호·페이지 크기를 검증한다.
- 검색 결과에는 요약 필드만 반환한다.
- 상세 조회는 canonical book ID 또는 ISBN13으로 제공한다.
- 상세 응답에는 로그인 사용자의 서재 상태·평점 상태를 포함한다.
- `WANT_TO_READ` 상태이면 프론트엔드에서 좋아요 버튼을 활성화 상태로 표시한다.

### API 예시

```text
GET /api/v1/books?query=데미안&page=0&size=20
GET /api/v1/books/{bookId}
```

### 완료 조건

- 제목으로 검색된다.
- 저자로 검색된다.
- 검색 결과가 없을 때 일관된 빈 결과 응답이 나온다.
- 로그인 사용자는 자신의 서재 상태와 평점을 확인할 수 있다.
- 비로그인 사용자는 공개 도서 정보만 확인할 수 있다.

## 10. 6단계 — 서재·독서 상태·좋아요

### 작업

- 서재 등록 API를 구현한다.
- 좋아요 버튼으로 `WANT_TO_READ` 상태 등록을 처리한다.
- 좋아요 취소로 `WANT_TO_READ` 서재 등록 취소를 처리한다.
- 독서 상태 변경 API를 구현한다.
- 상태별 목록 조회와 페이지네이션을 구현한다.
- `READ` 전환 시 완독일을 저장한다.
- `READING` 또는 `READ` 상태인 책은 좋아요 취소만으로 서재에서 삭제하지 않는다.
- 사용자 본인의 서재만 조회·수정·삭제하도록 권한을 검사한다.

### API 예시

```text
GET    /api/v1/library?status=WANT_TO_READ&page=0&size=20
POST   /api/v1/library/books/{bookId}
PATCH  /api/v1/library/books/{bookId}/status
DELETE /api/v1/library/books/{bookId}
```

### 완료 조건

- 같은 사용자가 같은 책을 중복 등록할 수 없다.
- 세 가지 독서 상태가 저장되고 조회된다.
- 좋아요 버튼과 `WANT_TO_READ` 상태가 항상 같은 값을 나타낸다.
- `READ`가 아닌 상태에는 완독일이 남지 않는다.
- 다른 사용자의 서재를 조회·수정·삭제할 수 없다.

## 11. 7단계 — 평점

### 작업

- 평점은 1~5 정수로 제한한다.
- 평점 등록·수정·삭제를 구현한다.
- 선택 감상평 등록·수정·삭제를 구현한다.
- 사용자당 도서별 평점 1개만 저장한다.
- 평점 변경 후 상세 화면에 즉시 반영한다.
- 감상평은 본인 기록으로만 조회·수정하고, 빈 문자열은 null로 저장한다.
- 평점 4점 이상을 개인화 추천의 긍정 입력으로 사용한다.
- 감상평은 MVP 추천 계산·검색 색인·AI 분석에 사용하지 않는다.

### API 예시

```text
PUT    /api/v1/books/{bookId}/rating
DELETE /api/v1/books/{bookId}/rating
```

`PUT` 요청에는 `rating`(필수)과 `reviewText`(선택, 최대 300자)를 함께 보낼 수 있다.

```json
{
  "rating": 4,
  "reviewText": "전개가 빠르고 인물 묘사가 인상적이었다."
}
```

### 완료 조건

- 비로그인 사용자는 평점을 변경할 수 없다.
- 평점 범위를 벗어난 요청이 거부된다.
- 평점 중복 데이터가 생기지 않는다.
- 감상평이 선택적으로 저장되고 최대 길이·공백 정제 규칙이 적용된다.
- 감상평이 검색·추천 결과와 외부 사용자 응답에 노출되지 않는다.
- 본인 평점만 수정·삭제할 수 있다.

## 12. 8단계 — 콜드스타트 추천

### 목적

아직 `WANT_TO_READ`, `READING`, `READ`, 평점, 초기 취향 데이터가 없는 신규 사용자도 추천을 받을 수 있게 한다.

### 작업 순서

1. L1 수요 후보와 신간 후보를 준비한다.
2. 사용자의 출생연도·성별을 추천 세그먼트로 변환한다.
3. 세그먼트 인기 도서와 신간·수요 후보를 결합한다.
4. 초기 취향 설정을 했다면 관심 분야와 seed book을 후보 필터에 반영한다.
5. 이미 서재에 등록한 도서는 제외한다.
6. `SEGMENT_POPULAR`, `INITIAL_PREFERENCE`, `NEW_BOOK` 추천 이유를 만든다.
7. 세그먼트 데이터가 없으면 전체 수요 후보와 신간 후보로 폴백한다.

### 완료 조건

- 행동 데이터가 0건인 사용자도 추천을 받는다.
- 세그먼트 데이터가 없어도 빈 화면이 나오지 않는다.
- 추천 이유가 카드에 표시된다.
- 이미 서재에 등록한 도서는 추천에서 제외된다.

## 13. 9단계 — 콘텐츠 기반 개인화 추천

### 추천 입력

- `WANT_TO_READ` 상태 도서
- 평점 4점 이상 도서
- `READING` 또는 `READ` 상태 도서
- 초기 취향 설정에서 선택·평가한 seed book

> `reviewText`는 기록용으로만 저장하며 MVP의 추천 입력에서 제외한다.

### 계산 순서

1. L1 후보와 신간 후보의 제목·저자·책소개를 하나의 텍스트로 결합한다. 사용자 감상평은 결합하지 않는다.
2. 텍스트를 정규화하고 TF-IDF 벡터를 계산한다.
3. 사용자의 긍정 도서 벡터를 가중 평균해 사용자 프로필 벡터를 만든다.
4. 후보 도서와 사용자 프로필의 코사인 유사도를 계산한다.
5. `WANT_TO_READ`·평점·독서 상태별 가중치를 적용한다.
6. 이미 서재에 있는 도서는 제외하고, 텍스트 부족 도서는 사전 필터에서 제거하지 않는다.
7. `loan_24m + 4 × loan_3m` 수요 랭킹을 보조 신호로 결합한다. 누적 대출량 자체는 랭킹 주신호로 사용하지 않으며, 감상평도 MVP에서는 사용하지 않는다.
8. 상위 N개를 저장하고 rank·score·추천 이유를 함께 기록한다.

### 초기 가중치

```text
평점 5점: 1.0
평점 4점: 0.8
WANT_TO_READ(좋아요): 0.6
READ: 0.9
READING: 0.8
```

평점 1~2점 도서는 긍정 프로필 생성에서 제외한다. 수치는 설정 파일에서 관리하고 운영 중 조정한다.

### 추천 이유

- 같은 저자: `선호한 저자의 다른 도서입니다.`
- 같은 카테고리: `관심 있게 본 분야의 도서입니다.`
- 텍스트 유사: `최근 관심 도서와 책소개가 비슷합니다.`
- 세그먼트 인기: `비슷한 독자 그룹에서 많이 대출한 도서입니다.`
- 수요 인기: `최근 2년 동안 도서관에서 많이 대출된 도서입니다.`
- 최근 상승: `최근 3개월 대출 수요가 높은 도서입니다.`
- 신간: `최근 출간된 도서입니다.`

### 구현 방식

- Python `data/recommendation`에서 추천 계산을 수행한다.
- 계산 결과는 PostgreSQL `recommendations`에 저장한다.
- Spring Boot는 추천 결과 조회·제외·이유 응답을 담당한다.
- 추천 계산 실패 시 마지막 성공 결과 또는 콜드스타트 결과를 반환한다.
- 실시간 학습이나 별도 ML 서버는 만들지 않는다.

### 완료 조건

- 행동 데이터가 있는 사용자에게 콘텐츠 기반 추천이 제공된다.
- 추천 결과가 매번 같은 도서만 반복하지 않는다.
- 추천 결과에서 서재 도서를 제외한다.
- 각 추천 결과에 `reasonType`, `reasonText`가 존재한다.
- 추천 계산 실패가 검색·서재·인증 기능에 영향을 주지 않는다.

## 14. 10단계 — 프론트엔드 통합·측정 이벤트

### 화면 구현 순서

1. 공통 레이아웃·헤더·로그인 상태
2. 회원가입·로그인
3. 초기 취향 설정
4. 검색 결과
5. 도서 상세
6. 서재와 독서 상태 필터
7. 좋아요(읽고 싶은 책) 등록·취소, 평점·감상평 입력
8. 추천 카드·추천 이유 요약
9. 추천 이유 상세 모달

### 이벤트

- 추천 카드가 화면에 노출되면 `IMPRESSION`
- 사용자가 추천 카드를 클릭하면 `CLICK`
- 사용자가 추천 이유 상세를 열면 `REASON_VIEW`
- 이벤트 실패는 사용자 화면을 막지 않고 실패 허용으로 처리한다.

### 완료 조건

- 목업 데이터로 화면을 먼저 확인한 뒤 실제 API를 연결한다.
- 로딩·빈 결과·오류 상태가 모두 표시된다.
- 좋아요 버튼 상태와 `WANT_TO_READ` 상태가 일치한다.
- 추천 이유 요약과 상세 내용이 같은 추천 결과를 가리킨다.
- 이벤트가 중복 전송되지 않는다.

## 15. 11단계 — 테스트·베타·배포

### 테스트 순서

1. 데이터 정제·ISBN 중복 제거 테스트
2. 회원가입·로그인·권한 테스트
3. 검색·상세 조회 테스트
4. 서재 상태 전이 테스트
5. `WANT_TO_READ` 중복·취소, 평점 범위·감상평 길이 테스트
6. 콜드스타트 추천 테스트
7. 콘텐츠 추천·추천 이유 테스트
8. 추천 계산 실패 폴백 테스트
9. 핵심 사용자 E2E 테스트

### 베타 시나리오

```text
신규 사용자 가입
 → 출생연도·성별 입력
 → 초기 취향 설정 또는 건너뛰기
 → 도서 검색
 → 도서 상세 확인
 → 좋아요(읽고 싶은 책) 등록
 → 읽는 중으로 변경
 → 평점 등록
 → 한 줄 감상평 기록(선택)
 → 추천 확인
 → 추천 이유 확인
```

### 베타 완료 조건

- 행동 데이터가 없는 신규 사용자도 추천을 받는다.
- 기존 사용자는 개인화 추천을 받는다.
- 추천 이유가 항상 표시된다.
- 인증·권한 오류가 없다.
- 외부 API 키와 JWT Secret이 노출되지 않는다.
- 검색·서재 기능은 추천 계산 실패에도 동작한다.
- Docker Compose로 로컬 재현이 가능하다.

## 16. 작업 요청 방법

앞으로 구현을 요청할 때 아래 형식을 사용합니다.

```text
[단계] 6단계 서재·독서 상태·좋아요 구현
[범위] WANT_TO_READ 등록·취소, READING·READ 상태 변경, finishedAt 처리
[선행] 3단계 저장소와 5단계 도서 상세 API가 준비되어 있다고 가정
[제외] 별도 Like 테이블·Like API·추천 알고리즘은 구현하지 않음
[완료] 문서의 6단계 완료 조건을 만족하고 테스트 결과 보고
```

### 작업 시작 규칙

1. 현재 브랜치·변경 사항·기존 구현을 확인한다.
2. 관련 문서와 데이터 모델을 먼저 읽는다.
3. 이번 요청 범위를 벗어난 코드는 만들지 않는다.
4. 구현 전에 API 계약과 기존 코드 호환성을 확인한다.
5. 코드를 작성한다.
6. 가능한 단위 테스트·통합 테스트·빌드를 실행한다.
7. 변경 파일, 실행 방법, 테스트 결과, 남은 결정 사항을 보고한다.

### 명령 예시

```text
0단계 진행해줘. 현재 저장소와 database 문서를 읽고 Book 공통 모델과 API 계약 초안을 작성해줘. 좋아요는 WANT_TO_READ 서재 등록으로 처리하고 별도 Like 모델은 만들지 마.

3단계 진행해줘. PostgreSQL Flyway 마이그레이션과 Elasticsearch books_v1 매핑을 구현해줘. 샘플 도서 저장·검색 테스트까지 포함해줘.

6단계 진행해줘. 인증된 사용자의 서재 등록·삭제·독서 상태 변경 API를 구현해줘. 좋아요는 WANT_TO_READ 등록으로 처리하고 READ 상태의 finishedAt 규칙을 지켜줘.

13단계 진행해줘. Python에서 TF-IDF·코사인 유사도 기반 개인화 추천을 구현하고 recommendations 테이블에 저장해줘. 이미 서재에 있는 책은 제외하고 추천 이유도 반환해줘.
```

## 18. 최종 MVP 완료 기준

- 회원가입·로그인·로그아웃이 동작한다.
- 출생연도·성별을 이용한 신규 사용자 세그먼트 폴백 추천이 동작한다.
- 초기 취향 설정을 저장하거나 건너뛸 수 있다.
- 제목·저자로 도서를 검색하고 상세 정보를 확인할 수 있다.
- 좋아요 버튼으로 도서를 `WANT_TO_READ` 상태로 서재에 등록할 수 있다.
- `READING`, `READ` 상태를 변경할 수 있다.
- 평점을 등록·수정·취소할 수 있다.
- 한 줄 감상평을 선택적으로 기록·수정·삭제할 수 있다.
- 감상평은 MVP 추천에 사용하지 않고 다음 버전 활용을 위해 안전하게 보관한다.
- 행동이 있는 사용자에게 콘텐츠 기반 개인 추천이 제공된다.
- 행동이 없는 사용자에게도 추천 결과가 제공된다.
- 추천 카드와 상세 영역에 추천 이유가 표시된다.
- 추천 노출·클릭·이유 확인 이벤트가 저장된다.
- 추천 계산 장애가 핵심 서비스 장애로 이어지지 않는다.
- 핵심 사용자 흐름이 베타 환경에서 처음부터 끝까지 성공한다.
