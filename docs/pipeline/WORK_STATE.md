## 5. 다음 작업 — 정보나루 본 보강

**엔드포인트**: `srchDtlList` (ISBN 당 1호출, `description` 회수)
부가: `keywordList` (키워드) — E층 91.7%, C층 38.3%, A/D층 10% 미만.
인기 신간에만 붙으므로 **수요 상위 구간에만 선별 호출**한다.

**실측 파라미터** (2026-08-27, 처음 보는 ISBN 기준)
| 워커 | 24 | 48 | 96 | 160 |
| --- | ---: | ---: | ---: | ---: |
| 건/초 | 5.0 | 6.4 | 7.6 | 7.4 |
| 지연 중앙 | 4.9s | 6.9s | 12.7s | 19.7s |

**서버가 7.5건/초에서 포화한다.** 워커를 늘려도 지연만 늘어난다.
포화 무릎인 **48워커** 채택 → 954,776건 ≈ **35시간**.

> 앞서 기록했던 "64워커 54.2건/초 / 4.3시간" 은 **틀린 값**이다.
> 같은 ISBN 750개를 반복 호출해 서버 캐시를 탄 측정이었다. 폐기.

**구현 완료** — `enrich_from_data4library.py`
- 3단 우선순위 큐, 락 파일, 단일 지점 쓰기, 200건마다 fsync
- 차단 시 전량 정지 → KST 자정 대기 → 자동 재개
- 재개는 출력 파일에서 완료 ISBN 자동 판별

**참고**: 수요 집중이 극단적이라 상위 6만 권 = 대출량 50%, 37만 권 = 90%.
전량을 다 긁기 전에 노출 가중 90% 에 도달한다.

**카카오는 이후 잔여분에만.** 정보나루로 못 채운 26.6% 중 카카오가 메우는 건
2.7%p 뿐이고, 그마저 C층(2015+ 신간)에 몰려 있다.

## 7. 반복된 사고와 교훈

- **프로세스 생존 확인**: Git Bash 에서 네이티브 Windows PID 는 판정 불가.
  `tasklist` 도 `kill -0` 도 거짓 음성을 낸다 (둘 다 실제로 당했다).
  **PowerShell `Get-CimInstance Win32_Process`** 로 볼 것.
  자동 감시에는 PID 대신 **출력 파일 증가량**을 쓰는 편이 안전하다
- **로그 파일 삭제**: 실행 중인 프로세스의 출력 대상을 지우면 죽는다. 로그는 저장소 밖에
- **CSV 필드 상한**: 회수 텍스트에 19MB 짜리 존재. `field_size_limit` 과 `MAX_CHARS` 동기화
- **인코딩**: utf-8/cp949 외 UTF-16 존재. 판별 실패 시 대체문자 대신 빈 문자열
