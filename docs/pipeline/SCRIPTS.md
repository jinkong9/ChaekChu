# 스크립트 색인

`database/_pipeline/scripts/` 의 파이썬 파일 전부. 14개.

실행 위치는 항상 `database/_pipeline/` 이다. 경로가 상대로 잡혀 있다.

```bash
cd database/_pipeline
py scripts/<이름>.py
```

원본 데이터는 저장소 밖 `project_personal/` 에 있다 ([DATA_INVENTORY.md](DATA_INVENTORY.md)).
`duckdb` 외 의존성은 없다.

<br/>

## 실행 순서

굵은 화살표가 실제 파이프라인이다. 나머지는 곁가지 측정·복구용이다.

```
국중 JSONL
   │ convert_nl_to_parquet
   ▼
nl_books.parquet
   │ measure_baseline            ← isbn_sql 사용
   ▼
nl_books_derived.parquet ─────────────────┐
   │ recover_nl_url_text                  │
   ▼                                      │
nl_url_text.csv                           │
   │ repair_url_text_csv (사고 시에만)     │
   │ merge_recovered_text ◄───────────────┘
   ▼
nl_books_enriched.parquet
   │ clean_text_for_embedding    →  nl_text_clean.csv (임베딩 입력)
   │
   │ build_enrich_queue          ← loans_by_isbn 사용
   ▼
enrich_queue.csv
   │ enrich_from_data4library
   ▼
d4l_enriched.jsonl


정보나루 관별 CSV 샤드
   │ build_holdings_parquet
   ▼
holdings / loans_by_isbn / libraries .parquet
```

<br/>

## 1. 변환·기준선

### `convert_nl_to_parquet.py` · 100줄
국립중앙도서관 `books_all_years.jsonl` (2.2GB, 204만 행) → Parquet (275MB, 6초).

**모든 컬럼을 VARCHAR 로 강제한다.** 자동 추론에 맡기면 ISBN 이 정수가 되어
`979` 접두와 선행 0 이 날아간다. 되돌릴 수 없는 손실이라 타입을 못 박았다.

### `isbn_sql.py` · 117줄
ISBN10↔13 정규화를 **순수 SQL 매크로**로 제공한다. 라이브러리가 아니라
다른 스크립트가 `import` 해서 커넥션에 주입하는 방식이다.

원래 파이썬 UDF 였는데 204만 행에 10분 넘게 걸려 전부 SQL 로 다시 썼다.
지금은 몇 초다.

- 정규화는 **10→13 단방향**만 한다. 13→10 은 `979` 접두에서 불가능하다.
- 숫자 변환은 전부 `TRY_CAST`. duckdb 는 `CASE`/`AND` 를 벡터 단위로 평가해서
  무효 행에서도 하위 식이 실행된다. `CAST` 를 쓰면 빈 문자열 하나에 질의가 죽는다.
- 자체 검증 8건 내장. `py scripts/isbn_sql.py` 로 단독 실행하면 돈다.

### `measure_baseline.py` · 377줄
Phase 0 전수 기준선. **API 호출 0회** — 전부 로컬 계산이다.

파생 컬럼(`isbn13_norm`, `add_kdc3`, `has_usable_text`, `pub_year` 등)을 붙여
`nl_books_derived.parquet` 을 만들고, 결측률·연도 분포·텍스트 보유율을
`reports/` 에 떨군다. 이후 모든 측정의 분모가 여기서 나온다.

<br/>

## 2. 국중 URL 텍스트 회수

국중 레코드에는 소개문 **본문 대신 `.txt` 파일 URL**만 있는 경우가 많다.
그 파일을 직접 받아오면 API 쿼터를 한 푼도 안 쓰고 텍스트를 늘릴 수 있다.
실제로 보유율이 6.95% → 13.02% 로 거의 두 배가 됐다.

### `recover_nl_url_text.py` · 197줄
`BOOK_INTRODUCTION_URL` / `BOOK_TB_CNT_URL` / `BOOK_SUMMARY_URL` 을 병렬로 받는다.
결과는 `nl_url_text.csv` 에 append — 중단해도 이어서 돌린다.

겪은 함정 두 가지가 코드에 박혀 있다.

- **인코딩**: utf-8/cp949 외에 UTF-16 파일이 섞여 있다. BOM 이 있으면 그것을
  우선 신뢰하고, 디코딩에 성공해도 대체문자(`�`)가 2% 를 넘으면 잘못 읽은
  것으로 보고 버린다. 이 검사가 없어서 1,832행이 깨진 채로 저장됐던 적이 있다.
- **초장문**: 최대 1,960만 자짜리가 있다. `csv.field_size_limit` 50MB,
  본문은 10만 자에서 자른다.

### `repair_url_text_csv.py` · 117줄
**사고 복구용.** 평상시엔 안 쓴다.

같은 파일에 두 프로세스가 동시에 append 하면 행이 찢어진다.
(프로세스 생존 확인을 잘못해 중복 기동한 적이 있다 — Git Bash 의 `tasklist` 는
신뢰할 수 없다. PowerShell 로 볼 것.)

찢어진 행은 **선언 길이(`chars`)와 실제 본문 길이가 어긋나는 것**으로 잡아낸다.
원본은 `.csv.corrupt` 로 보존하고 성한 행만 다시 쓴다.

### `merge_recovered_text.py` · 131줄
회수분을 `nl_books_derived.parquet` 에 병합해 `nl_books_enriched.parquet` 생성.
원본 필드는 지우지 않고 `r_intro` / `intro_final_len` / `has_text_final` 처럼
회수분을 따로 붙인다. 어느 쪽에서 온 텍스트인지 나중에 구분할 수 있어야 한다.

### `clean_text_for_embedding.py` · 192줄
임베딩 입력용 정제. **원문은 손대지 않고 별도 산출**한다 — 규칙이 바뀌면
원문에서 다시 만든다.

실측으로 확인한 오염 3종을 걷어낸다.

1. **필드 오분류** — `intro` 인데 내용이 목차. 표식(`차례`)이 없는 경우도 있어
   구조로도 판별한다 (장 표기 5회+ & 페이지번호 패턴 5회+ → `toc`)
2. **판권지 혼입** — 주소·전화번호가 섞여 있으면 '천안', '○○출판사' 가
   벡터의 신호가 되어 버린다
3. **목차 페이지번호** — `머리말 5` 의 숫자가 주제 신호를 흐린다

> 처리 순서가 중요하다. 장식 구분선(`······`)을 **먼저** 지워야
> `항목 ··· 12` 가 `항목 12` 가 되어 목차 판별이 성립한다.
> 장식 제거 → 재분류 → 페이지번호 제거 순.

`--sample 100` 으로 효과만 보고 끝낼 수 있다.

## 3. 정보나루 보유 원장

### `build_holdings_parquet.py` · 188줄
1,660개관 샤드 CSV → Parquet 3종.

| 산출 | 내용 |
| --- | --- |
| `holdings.parquet` | 1.21억 행. 관 × ISBN × 대출 × 권수 |
| `loans_by_isbn.parquet` | ISBN 합산. 필터·랭킹·우선순위의 근거 |
| `libraries.parquet` | 도서관 마스터 (libCode, 위경도) |

두 가지 정제가 빌드에 내장돼 있다.

- **체크섬 보정** — 원본 ISBN 에 체크디지트가 틀린 것이 섞여 있다.
  `978/979` 로 시작하는 13자리면 앞 12자리로 체크디지트를 다시 계산해 살린다.
- **도서관 이름 조인** — 샤드 파일명이 `장서/대출 데이터` 접미로 잘려 있어
  그대로는 안 붙는다. 접미 제거 + 접두 폴백으로 92.5% → **95.6%**.

### `analyze_nl_uncovered.py` · 233줄
국중에는 있는데 **어느 도서관도 소장하지 않은** 집합을 분석한다.
대출 임계 필터가 무엇을 버리는지 보는 용도.

여기서 나온 결론 하나: 정보나루에는 공공 1,165 + 작은 492 관만 있고
**대학도서관이 0곳**이다. 그래서 미소장 = "안 팔리는 책" 이 아니라
"공공도서관 유통망 밖의 책" 이고, 학술서는 과대 계상된다.

## 4. 보강 능력 측정 (파일럿)

본 수집 전에 "얼마나 채울 수 있는가(K)" 를 층화 표본으로 미리 잰다.
층은 모집단 비례가 아니라 **약점이 드러날 곳** 위주로 잡는다.

층 정의: `A` ~2006 / `B` 2007-14 / `C` 2015+ / `D` 정보나루 전용 / `E` 대출 상위

### `pilot_kakao_coverage.py` · 284줄
카카오 도서 API 의 `contents` 확보율. 750건 층화 표본.
→ 사후층화 **K = 50.2%**

### `pilot_data4library_coverage.py` · 274줄
정보나루 `srchDtlList` 초판. A층만 측정하고 일일 500건 상한에 막혔다.

### `pilot_data4library_v2.py` · 205줄
IP 등록 후 재측정. **차단 시점의 누적 호출 수를 기록**하도록 만들어서,
남은 층을 재는 동시에 등록 반영 여부까지 한 번에 확인한다.

960호출 완주 → 등록 확인. 그리고 결과가 계획을 뒤집었다.

| | K |
| --- | ---: |
| 카카오 단독 | 50.2% |
| **정보나루 단독** | **70.7%** |
| 합집합 | 73.4% |

정보나루는 카카오 위에 +23.1%p 를 더하는데 카카오는 정보나루 위에 +2.7%p 뿐이다.
근거는 [RECOMMENDATION_DATA_DECISIONS.md](RECOMMENDATION_DATA_DECISIONS.md) §8.

보강 대상 954,776건의 **우선순위 큐**를 만든다.
전량을 다 긁기 전에 멈출 수 있다는 전제로, 멈춘 시점까지가 가장 값어치 있게 정렬한다.

| 단 | 건수 | 기준 |
| --- | ---: | --- |
| 1 노출 90% | 301,154 | 누적 대출이 전체의 90% 에 닿을 때까지 |
| 2 신간 | 120,877 | 2025+ 발행. 대출 이력이 없어 1단에 못 드는데 추천 품질엔 직결 |
| 3 꼬리 | 532,745 | L1 후보 중 나머지 |

### `enrich_from_data4library.py` · 348줄
큐 순서대로 `srchDtlList` 를 호출한다. ISBN 당 1호출.

**동시성** — 서버가 7.5건/초에서 포화한다. 워커를 24→160 으로 늘려도
스루풋은 5.0→7.4 로만 오르고 지연이 4.9초→19.7초로 늘 뿐이다.
더 세게 밀어도 얻는 게 없어 포화 무릎인 **48워커**를 쓴다.

> 앞서 "54건/초" 로 측정한 적이 있는데 **잘못된 값**이다.
> 같은 ISBN 을 반복 호출해 서버 캐시를 탄 것이었다.
> 처음 보는 ISBN 은 호출당 7~9초 걸린다.

**안전장치** — 전에 겪은 사고를 그대로 막는다.

- 락 파일 + PID 확인으로 **중복 기동 금지**
- 쓰기는 **단일 지점에서 락**을 잡는다 (여러 곳에서 append 하면 행이 찢어진다)
- 차단 응답(`500건`/`IP`/`초과`)이 오면 전량 정지 → KST 자정까지 대기 → 자동 재개
- 200건마다 `fsync`. 강제 종료돼도 거기까지는 남는다
- 재개는 출력 파일에서 완료 ISBN 을 읽어 자동 판별. 깨진 줄은 미처리로 봐서 재시도

**남기는 필드** — 응답에 있는 것 중 쓸모 있는 건 다 남긴다.

| 필드 | 왜 남기나 | 채움율\* |
| --- | --- | ---: |
| `desc` | 주 목적. 임베딩 입력 | 95.0% |
| `class_no` `class_nm` | KDC. **국중에 없는 정보나루 전용 33만 건의 분류를 메운다** | 99.0% |
| `add_symbol` | 부가기호 → 독자대상·발행형태 (아동/전자책 판별) | 99.3% |
| `img` | 표지. 서비스 UI 에 필요 | 96.0% |
| 서지 4종 | 국중 미수록 건의 유일한 서지 | 100% |
| `age` `gender` | 연령대·성별 대출 분포와 순위. **콜드스타트 개인화 신호** | 54.5% |

\* 1단(수요 상위) 300건 표본. 꼬리로 갈수록 낮아진다.

`desc` 100자 이상은 1단에서 **89.7%** — 파일럿 평균 70.7% 보다 훨씬 높다.
우선순위 정렬이 그만큼 유효하다는 뜻이다.
